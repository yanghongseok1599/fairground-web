# 웹 경기 진입 대기 복구

사용자는 모바일에서는 첫 10시 경기에 들어가지만 웹에서는 ‘경기와 선수 명단을 준비하고 있습니다. 같은 경기가 다른 탭에 열려 있다면 닫아주세요.’에 멈춘다고 보고했다.

## 확인한 증상

운영 정식 주소의 동일 첫 경기를 관리자 계정으로 열어 18명 명단, 예정 상태와 0:0을 확인했다. 경기 시작·이벤트 입력·종료는 실행하지 않았다. 같은 브라우저·계정으로 두 번째 탭을 열면 사용자 사진과 같은 문구가 계속 표시됐고, 첫 탭을 닫으면 두 번째 탭이 정상 진입했다. 다른 기기는 해당 브라우저 Web Lock을 공유하지 않는다. 사용자의 Chrome 안에서 다른 탭이 실제 열려 있었는지까지 확인한 것은 아니다.

## 초기화 결함과 보호 조건

- 준비 상태 문구가 실제 다른 탭의 잠금 대기와 기기/서버 읽기 지연을 구분하지 않았다.
- 잠금 안에서 진행 중인 초기 읽기가 끝나지 않으면 화면 정리 신호를 보낸 뒤에도 잠금 callback이 끝나지 않아 다음 진입을 막을 수 있었다.
- 어댑터 생성 전에 current를 바꿔 생성 실패를 초기 오류로 표시하지 못하는 경로가 있었다.
- HTTP 계층의 제한시간은 인증 토큰 대기와 IndexedDB 대기를 포함하지 않았다. 스냅샷에 포함된 라인업도 별도로 다시 조회하고 있었다.

기기별 단일 기록자 잠금, 권한 검사와 지속 저장 대기열을 유지한다. 다른 탭의 잠금을 빼앗거나 저장 데이터를 초기화하지 않는다. 초기화 종료/취소와 늦은 결과를 구분하고, 초기 저장 트랜잭션까지 취소할 수 있어야 한다. 실제 다른 탭을 기다릴 때에는 서버 오류로 오인하지 않고 그 탭이 나가면 자동 진입해야 한다.

상태 안내는 [Lazyweb 오류/재시도 화면 참고](https://www.lazyweb.com/agentic-search/0ad70bf6-5916-4fa1-9ece-39f6f6b84c2a)의 오류 가시성과 명확한 복구 경로만 참고했다. 기존 레이아웃과 경기 운영 동선은 유지한다.

## 검증

구현 후 회귀 테스트, 실제 브라우저 IndexedDB 취소 검증, 개발·운영 카탈로그 대조와 정상 빌드, 자동 Preview 및 운영 상태를 아래에 기록한다. 이번 수정은 운영 DB 스키마·데이터를 변경하지 않는다.

초기화를 `room-session.ts`와 `room-bootstrap.ts`로 분리했다. 준비에만 30초 제한을 적용하고, 늦은 응답은 무효화하며 잠금을 잃은 이전 어댑터의 추가 입력을 차단한다. 다른 탭이 정상 기록 중인 대기는 시간으로 종료하지 않는다. 초기화·새로 조회한 상태 병합에는 선택적 AbortSignal을 전달하고, 실제 사용자 입력의 저장에는 전달하지 않아 이미 수락한 기록을 보존한다.

진입·공유 연결 회귀 21/21, 대기열·제어·복구 회귀 31/31을 통과했다. 네이티브 Chromium IndexedDB에서도 초기 취소, 실제 put 이후 롤백, 정상 커밋, DB 열기 중 취소 후 재시도, 신규 초기화 재시도, 커밋 후 늦은 취소를 포함한 6/6을 확인했다. TypeScript와 전체 Lint는 오류 0(기존 경고 16건), 개발·운영 카탈로그는 타입 컬럼 365개·조회 99개로 통과했다. 정상 운영 빌드도 성공했다.
