# 2026-09-30 Supabase 반복 장애 진단

결론: **운영 프로젝트는 이미 Pro 플랜 / Micro 1GB이므로 무료 플랜의 휴면을 원인으로 볼 수 없다.** 9월 21일·28일·30일의 DB 연결 불가와 재시작 후 복구는 기록으로 확인했다. 메모리·사진 조회 부담은 개선 대상이지만 장애의 직접 원인은 아직 확정하지 못했다. 유료 플랜 변경이나 서버 증설만으로 재발 방지를 보장하지 않는다.

## 확인 범위

- 대상: FairGround 운영 `ovtnmslyjzvghirdvife`, 2026-09-30 약 15:20–15:32 KST.
- Management API, 읽기 전용 DB 쿼리, Supabase Dashboard, 기존 복구 기록을 확인했다.
- Dashboard의 조직 표시가 **PRO**, 프로젝트가 **main / PRODUCTION**임을 확인했다.
- `/billing/addons`의 현재 선택은 `ci_micro`: RAM 1GB, 공유 CPU 2코어, 직접 DB 연결 최대 60개다.
- 이번 진단에서는 재시작, 결제 변경, DB 쓰기, 스키마 변경, OAuth 변경, 배포를 하지 않았다.
- 진단 원본과 Dashboard 화면은 상위 작업공간 `output/ops/2026-09-30-supabase-diagnosis/`에 보관한다. 계정 사진·이름·연락처 원문을 내려받지 않고 집계만 조회했다. 인증 비밀은 기록하지 않았다.

진단 시 서비스별 health는 정상이었다. DB 클라이언트 연결은 10/60개, 잠금 대기는 0개, 10초 초과 활성 쿼리는 0개였다. 이는 **복구 이후 시점**의 상태이며 장애 직전 상태를 증명하지 않는다. 최근 하루의 시간별 API 집계 최대는 606건/시간으로 지속적인 대규모 트래픽은 드러나지 않았지만, 짧은 요청 집중이나 개별 대용량 조회는 제외할 수 없다.

## 자원 지표의 의미와 한계

Dashboard의 24시간 범위에서 확인한 실제 툴팁 값이다. 화면의 MB 표기를 그대로 옮긴다.

| 시점 (KST) | Used | Cache + Buffers | Free | Swap | CPU |
| --- | ---: | ---: | ---: | ---: | ---: |
| 09-30 10:29:55 | 386.88MB | 417.68MB | 99.70MB | 642.97MB | 1.19% |
| 09-30 15:29:55 | 304.24MB | 553.63MB | 46.40MB | 284.95MB | 1.47% |

두 시점의 물리 메모리 Total은 904.27MB다. 헤더의 이 수치를 애플리케이션이 전부 소비한 메모리로 해석하면 안 된다. Free가 작아도 회수 가능한 캐시가 있다. 별도 현재 Prometheus 표본의 MemAvailable은 약 558MB였다. 스왑 사용은 확인했지만 현재 과부하나 과거 OOM을 단독으로 증명하지 않는다.

Memory commitment는 오전 2.13GB, 오후 1.54GB, commit limit은 1.44GB였다. commitment는 실제 물리 RAM 사용량과 다르다. 현재 부팅 이후 OOM 카운터는 0이지만 재시작 이전의 OOM 여부를 배제하지 못한다. 디스크 IOPS·연결 이력 등 여러 Dashboard 차트는 로드 실패여서 장애 직전의 디스크 I/O 고갈과 연결 포화를 판단할 자료가 부족하다.

DB는 약 186MB이며, 복구 직후 파일시스템 사용량은 약 0.53GB/8.42GB였다. 저장 공간이 가득 찼다는 증거는 없다. 무료 플랜의 500MB DB 제한도 현재 유료 프로젝트에 해당하지 않는다.

## 확인된 애플리케이션 부담 요인

운영 `profiles` 122행에서 사진 컬럼의 텍스트 합계는 다음과 같다.

- `photo_url`: 75,286,305 bytes.
- `profile_photo_url`: 77,461,757 bytes.
- 합계: **152,748,062 bytes, 약 153MB**. DB 전체 크기와 별개의 논리적 텍스트 크기다.
- `data:image/` 형식으로 DB에 직접 저장한 행: 각각 71건, 74건.
- 두 컬럼에 동일한 긴 사진 문자열이 중복된 행: 65건.
- 사진 문자열 하나의 최대 크기: 2,813,726 bytes.

현재 소스의 `src/stores/dataStore.ts`에서 `fetchPlayers()`는 관리자 RPC 전체 필드를, `fetchPublicPlayers()`는 두 사진 필드를 포함한 공개 선수 목록을 조회한다. 관리자 알림·징계·심판 화면에 전체 관리자 조회 호출이 남아 있다. 이는 조회량과 JSON 응답 크기를 키우는 구조다. 현재 브랜치 소스 확인 결과이며 이번에 운영 배포 파일 전체와의 일치까지 검증한 것은 아니다.

운영에서 이미 확인된 관련 사례도 있다. 9월 21일 승인 화면 개선 전에는 선수 86명의 전체 응답이 약 91MB였고 약 25초 후 시간 초과가 발생했다. 승인 화면에 필요한 필드만 조회하도록 수정한 응답은 약 21KB였다. 그 개선은 승인 화면에 적용됐으며 사진 저장 구조 전체를 바꾼 것은 아니다.

이 구조는 개선할 이유가 충분하지만, 위 조회가 9월 30일 DB 전체 장애를 직접 촉발했다고 확인한 요청 로그는 없다.

## 다음 조치 우선순위

1. 선수 사진을 별도 파일 저장소로 옮기고 DB에는 경로만 저장하도록 설계한다. 원본 해시 검증·접근 정책·백업·되돌리기 절차를 준비한 뒤 운영 이전을 별도로 수행한다.
2. 목록 조회를 화면별 필요한 컬럼으로 제한하고 전체 선수/사진 조회를 페이지 단위 또는 상세 진입 시 조회로 나눈다. 관리자 권한과 현재 사진 잠금 규칙을 유지한다.
3. 장애 전후의 메모리·스왑·디스크 I/O·연결 수·요청 크기와 서버 오류를 함께 수집하여 원인을 좁힌다. Supabase 지원팀에는 3회 발생 시점과 프로젝트 참조값을 근거로 호스트/OOM/서비스 로그 확인을 요청할 수 있다. 이번에는 문의를 전송하지 않았다.
4. 사진 조회 개선 이후에도 실제 메모리 압박이 확인되면 Micro에서 더 큰 compute로 변경을 검토한다. 비용이 발생하는 변경은 이번 진단에 포함하지 않았다.

Supabase 공식 상태 페이지에는 미 동부에서 접속하는 클라이언트의 지연 공지가 있었다. 프로젝트 지역과 무관하게 해당 지역 서버·함수 호출이 영향받을 수 있으나, 우리 장애와의 연관성은 아직 확인하지 못했다. 현재 증거로 플랫폼 전체 장애 또는 애플리케이션만의 문제라고 단정하지 않는다.
