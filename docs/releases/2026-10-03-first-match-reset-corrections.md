# 첫 경기 연습 기록 초기화와 심판 정정 버튼

사용자가 10시 첫 경기를 가상 운영한 뒤 해당 경기 초기화와 골·도움·경고 입력 실수 정정 수단을 요청했다. 기존 이벤트 타임라인의 취소 기능을 일반 빠른 기록, 전체화면 기록, 경기장 화면에서 바로 찾을 수 있도록 `기록 수정·취소` 진입과 공통 확인 창을 추가했다. 항목을 선택하고 확인한 뒤 취소하며, 올바른 기록은 선수별 버튼으로 다시 입력한다. 골과 도움은 별도 기록이고 직접 퇴장은 경고 누적 자동 퇴장과 구분한다. 종료 후 확정 기록은 이 UI에서 바꾸지 않는다.

## 운영 데이터 초기화

- 대상은 ROOT FC B팀 대 FC LEGACY, 경기 `4f0e7146-9229-4e91-94cf-add5c20275b7` 한 건.
- 2:2로 종료된 24초 연습의 이벤트 7개, 선수 4명 기여 통계, 자동 배지 5개, 두 팀 성적, 종료 활동 1개를 정확히 역산했다.
- 경기·대회·명단·사진·선수 신원·수동 등급/스킨/배지는 보존했다. 다른 종료 경기가 없음을 확인했으며, 다른 경기와 무관한 행은 변경 전후 해시로 보호했다.
- `scheduled`, 0:0, 00:00, 이벤트 0으로 돌아갔다. 기존 작업 영수증 18개를 그대로 유지하고 shared revision은 28→37, clock version은 4→5로 증가했다. 실제 운영 화면에서도 동기화 완료와 시작 버튼을 확인했다.
- 새 스키마 덤프 601,796바이트를 격리 복원해 정의 5,120개, 권한 250개, 이력 77건을 대조했다. public 32개 테이블의 민감 백업은 접근을 제한한 ops 폴더에 보관했다. 운영 DDL·마이그레이션 이력 변경은 없다.
- 실제 개인정보를 로컬 DB에 복사하지 않고 합성 데이터를 실제 RPC로 만들어 초기화·롤백·18개 UUID 재전송·오래된 시작 거부 등 8개 검증을 통과했다. 커밋 직후 확인 조회의 세션 역할 해제로 읽기가 실패했으나 초기화는 재실행하지 않았다. 별도 읽기 전용 세션에서 커밋된 32개 테이블 해시와 최종 상태를 재확인했다.

## 취소 동작 검증

- 기존 durable cancel 명령과 UUID 멱등 처리를 사용한다. 자동 퇴장의 원인 경고 ID를 기존 DB 컬럼에서 매핑해 서버 저장 후에도 경고 취소가 기기 화면에 즉시 투영된다. 직접 퇴장은 보존된다.
- 기록·공동 기록·종료 DB 테스트 21개와 취소 관련 DB 테스트 3개 통과. 동시 중복 취소, 원본 득점의 늦은 재전송, 도움 개별 취소, 자동 퇴장만 해제, 종료 후 취소 거부와 최종 집계를 검증했다.
- UI 정정·전체화면·빠른 기록 14개, 기기 저장/재전송/제어 복구 28개, 서버 스냅샷 ID 변환 1개, Supabase 안전 테스트 4개 통과.
- 로컬 실제 브라우저의 합성 선수로 골→취소→0점, 도움 유지→별도 취소를 확인했다. 일반·전체화면·경기장 모드에서 공통 정정 창이 열렸다. 임시 로컬 검증 경로는 배포 소스에서 제거했다. 실제 경기에는 테스트 기록을 새로 넣지 않았다.
- TypeScript, Lint(기존 경고 16개/오류 0), 개발·운영 카탈로그 정합성(타입 366/조회 99), 정상 `vercel build --prod` 통과. CLI 이력 조회는 격리 checkout의 IPv6 연결 문제로 실패하여, 검증된 TLS 연결로 읽은 원격 이력 77건의 전후 동일성을 사용했다.

근거와 배포 최종 상태는 `output/ops/2026-10-03-first-match-practice-reset`에 별도 보관한다. Lazyweb 추가 조회는 HTTP 429로 제한되어 기존 운영 UI 패턴과 이전 수집 근거를 사용했다. 실제 기기의 IndexedDB 대기열은 삭제하지 않았다. 서버가 아직 모르는 오프라인 작업까지 무조건 없다고 보장하지 않는다.
