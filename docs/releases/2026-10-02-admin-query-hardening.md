# 관리자 목록의 대용량 사진 조회 제거

심판·징계·푸시 관리가 `fetchPlayers()`로 전체 관리자 프로필을 요청해 화면에 필요 없는 사진까지 다운로드했다. 2026-10-02 진단 당시 132명 프로필의 두 사진 컬럼은 약 153MB였고, 운영 Postgres 로그에는 `get_admin_profiles`를 포함한 쿼리의 statement timeout이 확인됐다. 전체 서비스 장애가 OOM 때문이라는 증거는 확보하지 못했다.

## 반영 범위

- `features/admin-directory`에서 심판·징계·알림 대상·감독 승인용 DTO와 명시적 조회 컬럼을 관리한다.
- 심판은 서버에서 `role=referee`, 감독 신청은 `team_role=coach, is_approved=false`로 필터링한다.
- 심판·감독 사진은 기존 승인 화면과 같은 `사진 보기` 버튼으로 해당 한 명만 읽는다. 사진 원본·공개 범위·동의·잠금값은 변경하지 않는다.
- 오류를 빈 배열로 삼키던 전체 관리자 조회를 제거했다. 조회 실패는 경고와 `다시 시도` 버튼으로 표시한다.
- 심판·징계·푸시 조회는 12초 제한, 재조회/페이지 이동 시 취소, 오래된 응답 무시를 적용한다. 감독 신청 조회도 12초 제한을 적용한다.
- 심판 승인/역할 및 징계 저장 실패 후 서버 상태를 다시 읽고 저장 버튼을 복구한다. 알림 대상 로드 실패·수신자 계산 중에는 발송을 막는다.

## 검증

- `tsc --noEmit`, 전체 lint(오류 0, 기존 경고 16), 변경 파일 lint 통과.
- 관리자 목록·승인 로딩·등록 보존 41개, 심판 분류·팀 관리자 테스트 통과.
- Supabase 안전장치 4개, DB 배포 게이트 21개 통과.
- 실제 운영 카탈로그와 타입 계약 333개·조회 84개 대조 후 `npm run build`와 `vercel build --prod` 통과. DB 검사를 우회하지 않았다.
- 운영 DB에서 읽기 전용 트랜잭션/실제 관리자 JWT claim/`authenticated` 역할로 새 projection을 검증했다. 심판 5행 1,071바이트/22ms, 징계 132행 19,828바이트/192ms, 알림 대상 132행 13,244바이트/26ms, 감독 대기 0행 2바이트/28ms. HTTP/화면 전체 시간과는 다르다. `anon`은 거부됐다. [측정 근거](evidence/2026-10-02-admin-query-size.json).
- 로컬 운영 빌드에서 합성 관리자와 네트워크 대체 응답으로 네 화면의 실패→다시 시도→정상/빈 결과를 검수했다. 실제 운영 승인·징계·푸시는 실행하지 않는다. [브라우저 근거](evidence/2026-10-02-admin-browser.json).
- 오류 UX는 [Lazyweb 관리자 오류 복구 사례](https://www.lazyweb.com/agentic-search/488d5fba-e32f-433b-89cd-1a6b8a47c44e)를 참고했다.

## 사진 저장소 이전의 남은 조건

이번 릴리스는 웹 조회만 변경한다. DB 스키마·마이그레이션 이력·사진 데이터·회원 권한·경기 기록은 수정하지 않는다. SQL 백업을 새로 만들었다고 주장하지 않는다.

운영에는 공개 `team-galleries` 버킷만 있다. 여기에 회원 사진을 넣으면 미승인/정지 회원의 사진까지 공개할 수 있으므로 재사용하지 않는다. 공개 프로필 뷰는 현재 `is_approved=true AND is_banned=false` 조건을 가진다.

사진 이전에는 다음을 하나의 별도 검증된 변경으로 묶어야 한다.

1. 실제 운영 스키마의 복원 가능한 백업, 현재 이력과의 diff, 격리 DB에서 기준선과 단일 변경 재현.
2. 원본 해시를 유지하는 private 버킷, 소유자 업로드 제한과 관리자/공개 대상의 조회 권한; 모든 사진 표시·카드 내보내기 경로에서 접근 처리.
3. 신규 사진은 업로드 성공 후 주소만 저장. 업로드 실패 시 프로필을 변경하지 않으며 이전 앱의 인라인 쓰기도 확인.
4. 사진 한 개씩 백업→업로드→다운로드 해시 대조→DB 조건부 주소 변경. 이미 바뀐 사진은 덮어쓰지 않음.
5. 비사진 프로필·경기·동의·사진 잠금 필드 대조, 실패/되돌리기 검수, 저장소 정책과 웹을 함께 반영.

현재 전체 마이그레이션 이력이 호환되지 않고 빈 DB 재현이 불가능하다는 보호 상태는 그대로다. `fairground-supabase-safety/SKILL.md`의 “If any condition is missing, continue with read-only diagnosis and local safeguards; do not repair history or push schema changes.” 규칙을 따른다. 이번 조회 수정만으로 전체 Supabase 장애 원인이 모두 제거됐다고 단정하지 않는다.
