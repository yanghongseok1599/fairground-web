# 10시 경기 전 운영 연습 검증

사용자가 연습경기의 기록 공유를 확인한 뒤 삭제하도록 요청했다. 실제 대진과 선수는 사용하지 않고 고유 UUID의 연습 팀 2개·합성 선수 3명·대회 1개·경기 1개로 검수했다. 기존 순위 집계에 영향을 주지 않도록 종료 RPC는 실행하지 않았다.

## 운영 데이터 보호

운영 스키마 601,796바이트를 백업해 격리 PostgreSQL에 복원했다. 정의·컬럼 권한 5,120개, 별도 함수/테이블/스키마/기본 권한 250개를 대조했다. 로컬 복원에서 빠진 기본 public USAGE 한 건만 운영과 동일하게 맞췄다. 운영 DDL·권한·마이그레이션 이력은 변경하지 않았다.

동일 생성/기록/중지/삭제 절차를 복원 DB에서 먼저 실행해 32개 기존 public 테이블 행 해시가 동일함을 확인했다. 운영 생성 전후에도 기존 행을 대조했다. 팀 captain_id는 null이고 별도 시즌 연결과 다음 경기가 없어 실제 팀 알림·대회 일정에 연결되지 않는다.

## 첫 운영 브라우저 검수

심판 05는 정식 주소, 심판 04는 같은 운영 배포의 별도 origin을 사용했다. 두 계정에서 시작·양쪽 득점·도움·중지 상태를 공유했다. 04 탭을 오프라인으로 전환해 추가 골이 IndexedDB에 남음을 확인하고 재연결 후 양쪽에 1:2, 골 3건·도움 1건이 중복 없이 표시됐다. 두 기기의 해당 경기 pending은 0이었다.

연습 fixture가 없는 상태에서 32개 public 테이블 전체의 생성 전후 행 수·해시, 합성 auth 사용자 부재, 스키마·이력 77건의 동일함을 읽기 전용 확인했다. 실제 회원 132명과 경기 12개는 그대로였다. 단기 DB 인증 갱신 후 정리 명령이 이미 없는 fixture를 발견했으므로, 특정 삭제 호출의 성공으로 추정하지 않고 최종 부재/보존 검증을 별도 영수증에 기록했다. 사전 값으로 실제 데이터를 덮어쓰지 않았다.

## 검수에서 발견한 공유 연결 문제와 수정

실제 이벤트는 서버 저장됐지만 상대 화면의 대기 수가 과거 값을 포함했다. 설치된 `@supabase/realtime-js` 2.105.4의 Presence 변환이 Phoenix 내부 meta의 `phx_ref`를 제거해 갱신 항목이 누적되는 경로를 재현했다. 또 track 결과가 `timed out`/`error`이면 대기 0 전송을 재시도하지 않았고, 예상치 못한 CLOSED 후 채널이 SDK 목록에서 제거돼도 재가입하지 않았다. 최초 CLOSED의 발생 원인은 단정하지 않는다.

- 기기·기록자별 `queueRevision`(지속 저장된 room.revision)으로 최신 대기 수만 사용하고, 최신 0 이후 늦은 과거 상태가 대기 수를 되살리지 못하게 했다.
- Presence 전송을 직렬화·병합하고 성공 응답을 확인한다. 실패하면 최신 값을 1–5초 간격으로 재시도하며 최신 상태를 해당 연결의 전송기로 보낸다.
- 예상치 못한 CLOSED는 비동기 채널 제거가 끝난 뒤 재가입한다. 사용자가 나간 화면의 채널은 다시 만들지 않고 이전 콜백을 무시한다.
- 실제로 연결을 잃은 기기의 알려진 미전송 기록은 시간 경과만으로 0으로 바꾸지 않는다. 실제 경기 IndexedDB 대기열을 초기화하지 않는다.

설치 SDK를 그대로 사용한 재현, 실패한 0 전송, 늦은 이전 응답, 중복 meta, CLOSED 재가입, 화면 종료 취소를 포함한 관련 테스트 44개와 TypeScript·변경 파일 Lint를 통과했다. 원래 기록 저장·RPC·종료 집계·회원 권한은 변경하지 않았다. 최종 운영 빌드·자동 Preview·수정 후 재연습 증거는 Git 외부 `output/ops/2026-10-03-live-rehearsal`에 보관하며, 검증 완료 후 아래에 결과를 갱신한다.


## SDK 참조 보존과 연결별 전송기

두 번째 운영 연습에서도 양방향 골·도움·오프라인 복구는 정상이고 서버 기록 4건·양쪽 대기 0을 확인했다. 종료 대신 중지한 뒤 정확한 fixture UUID만 삭제했으며, 실제 32개 public 테이블의 행 수·해시, 회원 132명·경기 12개, 스키마·이력은 동일했다. 두 기기의 해당 연습 IDB 항목도 백업 후 pending 0을 확인하여 제거했다.

추가 검수에서 참여자 정보가 사라지는 경우를 확인해 설치 SDK의 두 경로를 분리했다. Presence 콜백은 live meta를 변형하므로 경기 기록 채널에만 버전·구조 검사와 중복 방지를 둔 인자 복제를 적용한다. 원본 SDK 콜백 및 서버 프로토콜은 유지한다. SDK 내부 구조나 버전이 달라지면 이 호환 처리도 재검토한다.

별도로 SDK 채널 teardown은 진행 중 track 응답 callback을 제거해 Promise가 자체 timeout 뒤에도 미해결로 남을 수 있다. 설치 SDK를 네트워크 없이 사용해 이 경로를 재현했다. 새 채널은 별도 전송기를 소유하게 하여 이전 채널의 미완료 작업이 재연결을 막지 않게 한다. 기존 저장 대기열과 과거 채널의 늦은 응답은 새 연결 상태를 바꾸지 않는다.

실제 경기 종료·순위 집계는 앞선 격리 DB 회귀 테스트로 검증한 기능을 유지한다. 이번 운영 연습은 사용자 요청의 공유 확인 범위로 제한해 종료 RPC를 호출하지 않았다. 운영 최종 재검수 결과는 이어서 기록한다.

SDK 참조 보존·채널 제거 중 미완료 전송·재가입·오프라인·제어·복구 관련 테스트 42/42와 독립 코드 검토를 통과했다. 기존 결과 공유 OG 변경도 통합해 해당 테스트, 전체 TypeScript와 Lint(기존 경고 16건·오류 0)를 확인했다. 개발의 실제 배포 소스 카탈로그 대조는 타입 컬럼 365개·조회 99개로 통과했다.

## 최종 운영 재검수와 정리

통합 앱 `0e0db26`의 운영 배포 `dpl_BLpJGTyjFRvnKHevHZEmG82gWQFx`가 Ready이며 정식 도메인에 연결됐다. 자동 Preview `https://fairground-48b4g8xko-milestones-projects-d52c4dda.vercel.app`도 Ready를 확인했다. 정상 `vercel build --prod`에서 운영 카탈로그 365개 타입 컬럼·99개 조회를 대조했다. OG 폰트는 Vercel의 filePathMap을 통해 작업 폴더 원본이 업로드되는 구조까지 설치 CLI 코드로 확인했다.

새 운영 코드에서 심판 05와 04로 아래를 확인했다.

- 양쪽의 동시 득점과 도움을 공유했다. 기록 전송 RPC만 막아 한 기기에 남은 대기 1건이 상대에게도 보이며 종료를 기다리라는 상태가 표시됐다.
- 경기 채널을 강제로 제거한 뒤 약 1.15초 만에 새 채널로 재가입했고 두 기록자 이름이 복원됐다.
- 오프라인 골 입력이 기기에 저장됐고, 온라인 복구 후 서버·두 화면에 골 4건과 도움 1건, 점수 2:2가 중복 없이 반영됐다. 심판 04의 중지도 양쪽에 반영됐다.
- 마지막에는 양쪽 서버 스냅샷의 이벤트가 5건, pending이 0, error가 없고 두 이름 및 유효한 Presence 참조가 각 1행이었다.

검수 중 공유 연결이 일시 재접속되거나 중지 반영이 10초 이상 걸리는 순간도 있었다. 이후 자동 복구를 확인했지만, 관측하지 않은 전송/서버 원인을 단정하지 않는다. 검증 결과는 외부 서비스 무장애나 모든 상황의 즉시 전파를 보장하지 않는다. 단절 중 기록은 해당 기기에 보관되고 네트워크 복구 후 전송된다.

마지막 fixture는 중지와 pending 0을 확인한 뒤 서버 기록을 별도 보관하고 정확한 UUID 범위만 삭제했다. 삭제 후 실제 32개 public 테이블의 행 수·해시는 생성 전과 같고 회원 132명·경기 12개, 스키마 정의·이력 77건도 동일하다. 세 연습 fixture의 로컬 저장 항목만 별도 백업 후 제거했으며 실제 경기 대기열·사진·통계는 건드리지 않았다.

세부 영수증은 Git 외부 `output/ops/2026-10-03-live-rehearsal/after-sdk-fix`의 `pending-shared.json`, `offline.json`, `browser-final.json`, `server-proof.json`, `cleanup.json`, `browser-practice-cleanup.json`에 있다. 운영 DB 스키마·권한·이력 변경은 없고, 기존 linked push/reset/repair 금지는 유지한다.
