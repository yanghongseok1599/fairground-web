## 배포 직전 발견해 추가 수정한 문제

운영 `profiles`는 authenticated 역할에 전체 SELECT를 허용하지 않는다. `phone`, `email`, `gender`, `birth_date`, `has_player_experience`, `team_role`, `portrait_consent_at`은 직접 SELECT가 금지되어 있다. 따라서 12차의 `update/insert.select("*").single()`은 격리 테스트에서는 성공해도 운영 권한에서 거부될 수 있었다.

저장 시 `select("id").single()`로 실제 본인 행이 반영됐는지 확인한 뒤, 이미 운영 중이며 실행 권한이 있는 `get_my_profile()`로 정본을 재조회하도록 수정했다. 권한을 확대하거나 개인정보 공개 범위를 바꾸지 않았다. 재조회가 실패하면 저장 자체가 취소됐다고 단정하지 않고 결과 미확인 안내와 입력을 유지한다. 자동 재전송은 하지 않는다.

운영 카탈로그에서 컬럼별 권한, RLS, RPC 실행 권한과 반환 타입을 읽기 전용으로 확인했다. 실제 회원 행을 조회하거나 테스트 회원을 운영에 만들지는 않았다.

분리 디렉터리에는 환경변수를 복사하지 않았다. 첫 로컬 빌드는 공개 Supabase 설정 부재로 보호 장치가 차단했고, 이후 확인된 개발 환경의 공개 설정만 자식 빌드 프로세스에 전달해 통과했다. 실제 배포는 Vercel의 기존 Production 설정을 사용했다.

Vercel에는 `SUPABASE_DB_URL`이 없어 위의 최신 읽기 전용 카탈로그 검사를 별도로 완료한 다음, 해당 배포 명령에만 `--build-env FAIRGROUND_SKIP_DB_PARITY=1`을 사용했다. 상시 우회 환경변수를 추가하거나 게이트 코드를 변경하지 않았다. 기존 마이그레이션 이력 불일치는 그대로이므로 운영 SQL push/repair는 계속 금지한다.

## 남은 검증과 대책

1. 실제 로그인 계정의 두 사진 방식 선택→저장→재로그인 결과는 이 작업에서 직접 검증하지 못했다. 해당 테스트 계정 세션이 확보되면 화면 결과와 본인 조회 결과를 대조해야 한다. 카탈로그 검사와 격리 UI 테스트를 실제 인증 저장 테스트로 표시하지 않는다.
2. 실제 iPhone Safari의 HEIC·대용량 사진·모델 첫 로딩·연결 단절/복귀는 실기기 검증이 남는다. 실패한 파일은 취소하고 기존 사진/입력으로 돌아갈 수 있으며, 결과 불명 저장은 자동으로 재전송하지 않는다.
3. 기존 의존성 경고 5건(높음 1·보통 3·낮음 1)은 여전히 존재한다. 이번 배포에서 패키지/잠금 파일은 변경하지 않았다. 범위 밖 의존성 업데이트와 빌드/사진 처리 회귀를 별도 수행해야 한다. [기존 보안 기준선](../security-baseline.md) 참고.
4. 회귀가 확인되면 기준 배포 `fairground-g6ifyjs26-milestones-projects-d52c4dda.vercel.app`으로 운영 alias를 되돌릴 수 있다. DB 변경이 없어 DB 롤백은 필요하지 않다.
