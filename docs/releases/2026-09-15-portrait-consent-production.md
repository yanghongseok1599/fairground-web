## DB 백업과 적용 검증

1. 운영의 `public`, `auth`, `storage`, `extensions` 스키마를 custom-format 덤프로 백업했다. 회원 행은 개발/로컬로 복사하지 않았다.
2. 별도 로컬 PostgreSQL 17에 소유자·권한·정책·Auth 트리거를 복원했다. 공개 스키마의 함수 본문, 트리거, 정책, 컬럼, 인덱스, 컬럼 권한, RLS 플래그 4,482개가 운영과 일치했다.
3. 새 SQL 적용 전후를 비교했다. 변경은 함수 2개와 트리거 2개 추가뿐이며, 기존 비교 대상의 정의는 변경되지 않았다.
4. 새로 복원한 별도 리허설 DB에서도 운영 적용 트랜잭션을 실행했다. 실제 `authenticated` 역할과 RLS를 사용하는 회귀 테스트 8개를 통과했다.
5. 운영에서 대상 프로젝트, SQL 해시, 기존 마이그레이션 기록, 변경 전 스키마 해시를 확인하고 같은 SQL을 적용했다. 변경 후 해시가 리허설과 일치하는 상태에서 새 버전 한 건을 기록하고 커밋했다.

## 테스트와 운영 확인

- 운영 배포 소스: 린트 오류 0/기존 경고 18, TypeScript, 로컬·Vercel 빌드 통과.
- 운영 배포 소스의 동의/사진 회귀 테스트 20개, 가입 실명 테스트 5개 통과.
- 실제 운영 카탈로그와 운영 배포 소스의 DB 참조 150개 대조: 누락 0개.
- Vercel에 DB 연결 변수가 없으므로 이번 빌드 한 번에만 `FAIRGROUND_SKIP_DB_PARITY=1`을 전달했다. 사전 실카탈로그 대조로 보완했으며 프로젝트의 지속 환경변수는 변경하지 않았다.
- `tests/portrait-consent-production-schema.test.mjs`: 실제 스키마·권한을 복원한 로컬 DB에서 8개 통과. 가입 프로필 생성, 개인 동의 조회 권한, 미동의 카드 쓰기 차단, 동의 후 카드 쓰기/최초 시각 보존, 기존 회원 동의, 기존 신청 RPC 흐름, 팀 동의만 제출 시 차단, 타인 대신 동의 차단을 검증한다.
- 운영 도메인이 새 배포 ID를 가리키고 상태가 `READY`임을 확인했다. 운영 DB의 적용 후 해시도 리허설과 일치했다.
- Ego 브라우저로 운영 가입 화면의 기본 미체크/필수 체크/가입 버튼 비활성화를 확인했다. 체크하면 가입 버튼이 활성화됐다. 가입은 제출하지 않았다.
- 운영의 로그인된 미동의 상태에서 홈페이지 안내, 알림함의 동의 링크, 마이페이지 동의 카드, 카드 편집 직접 진입 차단, 개인 동의와 팀원 동의 확인의 별도 체크박스를 확인했다. 실제 회원의 동의를 저장하거나 대회 신청을 제출하지 않았다.

초상권 알림은 로그인한 미동의 회원에게 표시되는 앱 내부 알림이다. 외부 문자·푸시를 일괄 발송하지 않는다. 동의 완료 후 안내/알림 해제와 카드 저장은 앞선 로컬 합성 계정 검증 및 이번 실제 스키마 회귀 테스트로 확인했다.

## 복구 시 유의사항

직전 Vercel 배포 ID와 URL을 위에 남겼다. 웹만 되돌리면 새 DB 동의 규칙이 유지되므로 이전 가입/신청 화면에서 동의를 저장하지 못할 수 있다. 장애 발생 시 영향을 먼저 확인하고 웹과 DB의 동의 계약을 함께 맞춰야 한다. DB 변경이 필요하면 새 SQL 파일로 검증·기록하며, 이미 받은 동의 이력을 삭제하거나 운영 전체 덤프를 덮어쓰지 않는다.
