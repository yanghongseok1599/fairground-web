# 사진 용량과 경기 기록 조회 부하 개선

운영 복구 후에도 두 프로필 사진 컬럼에 153,276,524바이트의 인라인 이미지가 남아 있었다. 경기 기록 화면까지 이 사진들을 팀 명단과 함께 읽고 있어, 심판 진입에 불필요한 전송과 DB 응답 생성 부하가 발생했다.

## 웹 변경

- 경기 기록/중계의 명단 조회는 사진·소개 없이 이름, 등번호, 소속, 승인/징계, 경기 통계만 읽는다. 조회 실패는 빈 명단으로 바꾸지 않고 오류로 전달한다. 이 조회의 SDK 자동 재시도를 끈다.
- 신규 선수 사진과 프로필 사진은 저장 전에 최대 1,024px, 120KiB로 압축한다. 투명 배경을 유지하고 이미 처리한 WebP의 재압축을 피한다. 20MiB 초과 입력, 잘못된 이미지, 해상도 초과 및 처리 시간 초과는 DB 쓰기 전에 거부한다.
- 파일 선택뿐 아니라 보관된 초안/직접 store 호출에도 같은 검증을 적용한다. 실패 시 기존 사진을 유지한다.

## 기존 사진 데이터 반영

2026-10-03 00:26 KST 운영 프로필 60명의 사진 필드만 압축본으로 교체했다. 두 사진 필드 합계는 **153,276,524 → 49,429,191바이트(67.8% 감소)**다. 이는 논리 데이터 크기이며 DB 디스크 파일이 즉시 같은 비율로 줄어든다는 의미는 아니다.

- 인라인 사진 보유 75명 중 60명 압축, 1명 이미 작은 이미지, 14명 동의 기록 없음으로 변경 제외.
- 변경 이미지 118개를 디코딩 검사했다. 투명도 보유 117개 모두 알파 채널 유지, 최대 파일 122,764바이트, 가로·세로 비율과 1,024px 상한 확인.
- 원본 75명의 두 사진 필드와 해시를 권한 제한 폴더에 백업했다. 동의 기록을 생성하거나 기존 사진 잠금을 변경하지 않았다.
- 최신 579,105바이트 스키마 덤프를 별도 로컬 PostgreSQL에 실제 복원했다. 운영의 정의/권한/제약조건 4,805개와 일치했다. 실제 회원 데이터는 테스트 DB에 넣지 않았다.
- 복원 DB 합성 데이터로 사진 필드 외 보존, 오래된 사진 덮어쓰기 거부, 동의 없는 갱신 거부, 원본 복구/트랜잭션 롤백을 검수했다.
- 실제 교체는 원본 사진 해시가 일치하는 행만 갱신하는 단일 트랜잭션이다. 사진 외 프로필 컬럼, 30개 public 테이블의 보호 값, 변경 제외 72명 사진, 스키마와 마이그레이션 이력이 동일함을 트랜잭션 안에서 확인했다.
- 운영 DDL, RLS, 트리거, 권한 및 이력 수정 없음. 기존 마이그레이션 이력 불일치와 linked push/reset/repair 금지는 계속 유지한다. 본 작업은 이력 재구성 또는 Storage 전환이 아니다.

백업/상세 검증 자료: `/Users/seok/PROJECT_FESTIVAL/futsal project/output/ops/2026-10-03-photo-reliability` (원본 사진 포함, Git 제외, 폴더 0700/파일 0600).
복구가 필요하면 현재 사진이 압축본과 동일한지 확인한 후 `scripts/photos/compact-photo-data.mjs`의 비교 후 교체 함수를 반대로 적용하고, 사진 외 값 및 스키마/이력을 다시 대조한다. 백업을 무조건 덮어쓰지 않는다.

## 동의 상태와 무관한 기존 사진 용량 최적화

사용자가 기존 사진의 용량 최적화와 사진 내용 변경을 구분하도록 명시했다. 2026-10-03 01:02 KST 동의 기록이 없던 14명도 압축을 완료했으며 **동의 기록 14개는 모두 여전히 없음(null)**이다. 최종 합계는 **17,673,997바이트**, 최초 대비 **88.47% 감소**다. 사진이 있는 75명 중 74명의 145개 사진 필드를 압축했고, 이미 작은 1명은 유지했다. 최대 인라인 문자열은 163,711바이트이며, 120KiB 이미지의 base64 상한을 넘는 필드는 0개다.

운영 `20261003010000_inline_photo_compaction.sql`은 기존 동의 트리거 함수 1개의 분기만 추가했다. DB 소유자 소속의 원래 접속 세션이 정확한 기존/압축본 SHA-256 범위를 지정했을 때만 사진 필드의 용량 감소를 허용한다. 사진 이외 모든 값이 동일해야 하며 외부 URL 교체, 파일 증가, 이름/카드 설정 동시 변경은 거부한다. 일반 회원/서비스/API 역할은 이 경로를 사용할 수 없다. 운영에서 트리거를 끄거나 RLS/권한을 바꾸지 않았다.

유효한 백업/복원 기준과 운영 정의 일치를 재확인하고, 동일 SQL의 격리 DB 적용/롤백 및 추가 회귀 8개를 통과했다. 함수 변경·14명 사진 최적화·이력 1건 추가는 단일 트랜잭션이다. 사진 외 프로필 및 30개 public 테이블 보호 값, 나머지 118명 사진, 기존 마이그레이션 이력은 보존됐다. `authenticator`, `authenticated`, `service_role`의 실제 운영 DB 소유자 권한 없음도 확인했다. 전체 이력 재구성은 아니므로 linked push/reset/repair 금지는 유지한다.

원본 75명의 백업은 그대로 보존한다. 14명 작업은 트랜잭션 롤백으로 정확히 원복됨을 검증했다. 이후 압축본을 원본 크기로 다시 늘리는 복구는 축소 전용 함수에서 허용하지 않으므로, 백업 및 현재 사진 해시를 대조하는 별도 검수된 복구 절차가 필요하다.
