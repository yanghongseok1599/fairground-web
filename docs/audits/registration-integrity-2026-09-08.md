# 참가자 등록·수정·명의변경 점검 (2026-09-08)

## 상태와 범위

코드 수정과 격리된 로컬 검증을 완료했다. **운영 반영은 하지 않았다.** 실제 회원·팀·경기 기록을 수정하거나 개발 DB로 복사하지 않았다. 운영에서는 연결 대상, 원격 마이그레이션 목록, 스키마만 읽었다.

운영 회원 기록의 과거 유실 여부를 판정할 수 있는 전수 대조를 한 것은 아니다. 이번 결과는 소스와 실제 운영 함수·정책 정의에서 확인한 결함 및 수정 검증이다.

## 확인한 문제와 조치

| 문제 | 조치 |
| --- | --- |
| 팀 INSERT 이후 감독 연결·프로필 갱신이 실패하면 이미 만들어진 팀도 등록 실패로 표시 | `register_team` RPC가 팀 생성·감독 연결·이력을 한 트랜잭션에서 저장. 클라이언트는 이 RPC 한 번만 호출 |
| 응답 유실 뒤 다시 누르면 다른 팀이 만들어질 수 있음 | 요청 UUID를 재사용하고, 서버가 계정 단위 잠금 및 기존 등록 확인. 기존 저장과 팀명·로고·창단연도·유형이 다른 재시도는 입력을 버리지 않고 명시적으로 거절 |
| 팀 수정·선수 저장이 실제 DB 반영 확인 없이 성공처럼 보임 | 반환 행을 확인한 뒤 상태 갱신. 권한 때문에 0행이 수정되면 입력을 유지하고 오류 표시 |
| 명의변경 후 재조회가 오래된 캐시를 반환 | 명의변경 성공 즉시 캐시 갱신, 명시적 서버 재조회. 갱신 실패와 변경 실패를 분리 |
| 명의변경 동시 요청 및 소유자 NULL의 조건문 문제 | 팀 행 잠금 후 권한 판정, 대상 선수 행 잠금, NULL을 명시적으로 거절 |
| 변경 내역을 사후 대조할 등록 전용 이력이 없음 | 팀·선수·가입 신청의 중요한 변경 전후 값과 행위자·시각을 같은 트랜잭션에 기록. 일반 참가자는 이력을 읽거나 변경할 수 없음 |
| 감독 연결과 팀 가입이 겹치면 이전 소속을 덮어쓸 위험 | 감독 연결 함수가 팀→프로필 순서로 잠근 뒤 소속을 확인 |
| 가입 직후 기본 프로필 행이 있다는 이유로 일반 선수 설정 화면을 건너뜀 | 선수 설정 완료 여부로 이동 판단. 사진은 선택항목이므로 필수 입력과 제출 동의 시각으로도 완료 인정 |
| 선수 재등록이 기존 값·권한·배지 등을 다시 보내거나 로컬 프로필의 다른 필드를 잃음 | 서버에서 현재 프로필을 읽고 제출한 카드 필드만 수정. 소속·역할·통계·기존 동의는 다시 쓰지 않고, 커밋된 응답 행의 최신 값을 반영 |
| 인증 갱신이 편집 중 입력 또는 로그인 상태를 덮어씀 | 폼 초기화는 최초 계정 로딩에만 수행. 늦게 끝난 인증 조회·실패가 현재 사용자 상태를 지우지 못하도록 보호 |
| 읽기·이미지 오류가 무응답처럼 보이고 저장 버튼 연속 요청 가능 | 실제 HTTP 요청과 응답 본문을 25초로 제한, 파일 읽기 실패 전달, 동기 제출 잠금, 처리 중 입력 비활성화 |
| 팀 소개·로고·창단 연도를 지우면 화면과 서버가 달라짐 | 명시적 빈 입력을 서버의 빈 값/NULL로 저장. 빠진 키는 기존 값 보존 |
| 마이페이지 이름 수정에 가입 때 선택이었던 전화·성별·생년월일을 모두 강제 | 필수 이름·이메일을 확인하고, 선택 생년월일·성별의 빈 값은 NULL로 저장 |
| 이메일 인증 대기 중에도 로그인된 것처럼 화면 이동 | 세션 없는 가입은 인증 안내 후 로그인으로 연결 |
| 가입 신청 중복 제약 충돌이 오류로만 표시 | 이미 있는 승인 대기 신청을 조회해 같은 신청으로 복구 |

## 입력 보관

회원가입(비밀번호 제외), 선수 설정, 카드 수정, 팀 등록·수정, 혼성대회 팀 신청, 마이페이지 프로필 수정에 계정·폼별 임시보관을 적용했다. 같은 탭에서 새로고침·이동 후 복원하며 7일이 지난 데이터는 만료시킨다. 최종 압축 사진·로고도 포함한다. 서버 저장이 확인되기 전에는 보관본을 지우지 않는다.

브라우저 저장 공간이 부족하거나 사용을 차단한 경우 성공으로 표시하지 않는다. 현재 입력을 유지하고 화면을 닫지 말라는 안내 및 새로고침 경고를 제공한다. 탭 종료·브라우저 데이터 삭제·저장소 자체 손상까지 복구를 보장하는 서버 임시저장은 이번 범위에 포함하지 않는다.

## 운영 반영 순서와 미완료 조건

기준 문서: `AGENTS.md`, `docs/supabase-safety.md`, `/Users/seok/.codex/skills/fairground-supabase-safety/SKILL.md`.

해당 지침은 운영 변경 전에 호환되는 마이그레이션 이력, 유효한 복원 가능한 백업, 실제 스키마 diff, 개발/격리 DB 재현을 요구한다. 현재 **로컬·운영 마이그레이션 이력 불일치 및 전체 기준선 복구 미완료** 상태이므로 운영 변경은 진행하지 않았다. 스키마 덤프와 이번 증분 SQL의 로컬 검증만으로 이 조건을 충족했다고 판단하지 않는다.

1. 기준선·이력 불일치를 해소하고 전체 복원 및 개발 검증을 완료한다.
2. `20260908030000_registration_integrity.sql`의 실제 운영 diff를 검토한다. 현재 운영에 이미 있는 승인 대기 대표 수정 정책은 변경하지 않는다.
3. 검토된 동일 SQL을 통제된 배포 경로로 적용하고 `register_team` 존재, 이력 트리거 및 기존 권한을 확인한다.
4. 그 뒤 프런트엔드를 배포한다. **RPC 적용 전에 이 프런트엔드를 운영에 배포하면 팀 등록이 실패한다.** 기존 INSERT 방식으로 조용히 되돌리는 fallback은 넣지 않았다.
5. 실사용자 데이터를 건드리지 않는 확인 계정으로 등록·수정·명의변경을 검증하고, 운영 로그의 관련 오류 및 새 이력 적재를 확인한다.

과거에 이미 일부만 생성된 팀은 새 등록 함수가 같은 계정·팀명인 기존 팀을 재사용한다. 이름이 다르거나 다른 팀에 소속된 경우에는 자동 변경하지 않고 기존 등록 확인을 안내한다. 기존 선수·팀을 지우는 데이터 정리는 하지 않는다. 새 이력 테이블은 적용 이후의 변경부터 남긴다.
